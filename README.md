# retrieval-lab

混合检索(BM25 关键词 + 向量)的一组最小实现,以及四类**我实际踩到并修掉**的问题。

零外部依赖,`pytest` 直接跑:

```bash
PYTHONPATH=src python3 -m pytest tests/ -q
```

这个仓库的重点不是"实现了混合检索" —— 那是标准做法。重点是下面四件事:
**它们全部表现为"测试是绿的、指标是好的,而功能是坏的"。**

---

## 一、中文关键词检索完全失效,而所有测试都是绿的

SQLite FTS5 的 `unicode61` 分词器把**整个连续中文串当成一个 token**。索引侧存原文,查询侧生成二元组,两边永远匹配不上。

```
索引侧："数据库故障需要联系平台团队"  → 一个 token
查询侧："数据库故障"                → 数据 / 据库 / 库故 / 故障
结果：零命中
```

英文完全正常(`unicode61` 本来就在标点和空格处切),所以**测试用例全是英文的时候,这个 bug 隐形**。

**修法不是补一条中文测试,是把分词抽成单一来源** —— [`tokenize.terms()`](src/rlab/tokenize.py)。索引和查询都从这一个函数取词元,**靠结构保证一致,而不是靠约定**。

> 为什么是 bigram 而不是 unigram 或 trigram:单字太常见、没有区分力;trigram 会让"故障""薪资"这类**两字查询**完全无法命中,而两字查询是最常见的形态。

### 顺带一个可解释的取舍

FTS5 是隐式 AND,所以一个五字中文查询会变成四个 bigram 的 AND —— **精度很高但很脆**,任一 bigram 缺失就整条不命中。

这正是必须配向量路的原因,而且这个互补性是**可解释的**:关键词路管精确匹配(专有名词、错误码),向量路管语义近似。不是"混合更好",是两路各自覆盖对方的失效模式。

## 二、RRF 在小 top_k 下退化成抛硬币

RRF 的 `k=60` 刻意压平头部排名 —— rank 1 得 1/61、rank 2 得 1/62,**差距只有 1.6%**,这样任何单路的 top hit 都不能独断。

代价是:**融合需要候选深度**。如果每路只给 `limit` 条,`top_k=1` 时两路各交出自己的第一名,双方都是 1/61 —— **完全打平**,胜者由存储层的破平规则决定(一个后端按插入顺序、另一个按主键序)。

实测:同一个单查询 fixture,**12 轮里挂 8 轮**。

修法是[候选深度与 limit 解耦](src/rlab/fusion.py):`candidate_depth(1)` 返回 20,不是 1。

---

## 三、评测集四种配置全打 1.000,因为它零区分力

一套检索评测集,换四种不同配置(真/假 embedding × 两种向量后端)跑下来**全是满分**。看着完美,实际是:查询和目标文档字面重叠,关键词那一路单独就能命中 —— **真正想测的那一路做没做事,根本看不出来**。

> 一个永远打满分的评测集,和一个永远绿的测试一样没用。

修法是给**评测集自己**加守卫([`tests/test_evaluation_teeth.py`](tests/test_evaluation_teeth.py)):

- 查询与目标**不得共享** ASCII 词或 CJK 二元组
- 声明 `requires: semantic_embedding` 的 fixture 从"每个 fixture 都该满分"的全局断言里分流出去

比对函数**故意不复用生产分词器** —— 那只能证明两者互相同意,证明不了 fixture 有区分力。

## 四、目标文档排第一位等于白送分

第一版语义 fixture 跑出 `recall@k = 0.5`,我以为是"部分能力"。查下去发现**所有余弦精确为 0.0** —— 零信号。

那 0.5 从哪来的?把目标文档从第一位挪到最后,**分数掉到 0.25**,命中项也跟着换成新的首位文档。

> 平局时后端按插入顺序返回,而目标排在第一位 —— **零信号检索器的分数完全由哪篇文档先入库决定。**

修法:干扰项放前面,地板才真的是 0.000。并加一条守卫钉住这个布局要求。

---

## 每条守卫都做过变异验证

「永远绿的检查比没有检查更坏」——它同时给你虚假的安全感,并让下一个人以为这块已经有人管了。所以每条守卫都撤掉实现重跑,**必须精确报出预期的错误**:

| 变异 | 结果 |
|---|---|
| 索引侧改回写原文 | 分词测试 **7 红** |
| 查询混入目标措辞 | 区分力守卫 **1 红** |
| 目标文档挪到首位 | 布局守卫 **1 红** |

做这轮验证时我自己也踩了一次:第一次的变异脚本 `sed` 没匹配上(行尾多一个 `}`),文件根本没改,测试全绿 —— 我差点得出"守卫失效"的错误结论。**变异测试本身也需要先确认变异真的生效了。**

## 结构

```
src/rlab/
  tokenize.py     索引/查询共用的词元提取（单一来源）
  keyword.py      SQLite FTS5 + BM25，索引存词元、返回原文
  fusion.py       RRF + 候选深度决策
  evaluation.py   recall@k / MRR + fixture 完整性校验
tests/            每条测试对应一次真实事故
fixtures/         带 _why 字段说明它在测什么、为什么这么摆
```
